# Customer Management API

REST API для поиска пользователей по ИНН и КТРУ с проверкой статуса блокировки.
Объединяет данные из нескольких БД и ClickHouse-логов http-запросов.


## Проблема

При разборе инцидентов и подозрительной активности нужно было понять:

- С каких IP работал конкретный участник закупок
- Кто ещё заходил с этих же IP за тот же период
- Кто просматривал конкретный КТРУ или предварительное предложение
- Был ли пользователь ранее заблокирован заказчиком

Всё это лежало в разных источниках: БД пользователей и организаций, классификатор КТРУ,
БД целевого сервиса, ClickHouse с логами http-запросов. Собирать картину вручную — долго
и муторно.

## Решение

FastAPI-сервис с тремя эндпоинтами, каждый из которых собирает данные из нескольких
источников и возвращает готовый результат:

### `GET /search-by-inn`

Ищет пользователей-заказчиков по ИНН:
1. Находит всех активных пользователей организации по ИНН.
2. Через ClickHouse собирает уникальные IP, с которых они работали за N месяцев.
3. Отфильтровывает внутреннюю подсеть.
4. Ищет других пользователей, работавших с тех же IP по целевому URI.
5. Оставляет только заказчиков.
6. Проверяет статус блокировки каждого (заблокирован / разблокирован / никогда).

### `GET /search-by-ktru`

Показывает, кто просматривал конкретный КТРУ за указанный период:
1. Находит КТРУ в классификаторе.
2. Через ClickHouse ищет http-запросы к каталогу по этому КТРУ (`code = 200`).
3. Для каждого пользователя собирает уникальные IP и время просмотров.
4. Обогащает данными об организации и статусом блокировки.

### `GET /search-proposals`

Показывает, кто просматривал предварительные предложения организации:
1. По ИНН находит организацию.
2. По коду КТРУ — его ID в классификаторе.
3. В целевой БД находит все `proposal_information` организации, затем все `proposal`
   по этому КТРУ и дате.
4. По каждому предложению через ClickHouse ищет просмотры.
5. Агрегирует: какие ПП смотрел каждый пользователь, с каких IP, когда.

## Результат

- Ручной сбор данных из 4 источников → **один HTTP-запрос**
- Пакетная проверка статуса блокировки — один SQL-запрос на список пользователей,
  а не N запросов в цикле
- Единый формат ответа со всей информацией: пользователь, организация, IP, время,
  статус блокировки

## Стек

- Python 3
- FastAPI + Uvicorn
- Pydantic — валидация ответов
- SQLAlchemy (через внутренний `ConnectionFactory`)
- ClickHouse — анализ логов http-запросов
- Работа одновременно с несколькими БД и ClickHouse

## Эндпоинты

### `GET /search-by-inn`

| Параметр | Тип | Описание |
|---|---|---|
| `inn` | string | ИНН организации |
| `months_back` | int | Глубина поиска в месяцах |

### `GET /search-by-ktru`

| Параметр | Тип | Описание |
|---|---|---|
| `ktru_code` | string | Код КТРУ |
| `date_from` | string | Дата начала (`YYYY-MM-DD HH:MM:SS`) |
| `date_to` | string | Дата окончания (`YYYY-MM-DD HH:MM:SS`) |

### `GET /search-proposals`

| Параметр | Тип | Описание |
|---|---|---|
| `inn` | string | ИНН организации |
| `ktru_code` | string | Код КТРУ |
| `date_from` | string | Дата начала |
| `date_to` | string | Дата окончания |

### `GET /`

Описание API и список эндпоинтов.

## Пример запроса

```bash
curl -G "http://localhost:8000/search-by-inn" \
  --data-urlencode "inn=0000000000" \
  --data-urlencode "months_back=3"
```

## Запуск

```bash
git clone git@github.com:username/customer-management-api.git
cd customer-management-api
pip install -r requirements.txt

cp config.example.py config.py   # заполнить своими значениями
python main.py
```

Сервис поднимется на `http://0.0.0.0:8000`. Swagger-документация: `/docs`.

## Настройки (`config.py`)

| Параметр | Назначение |
|---|---|
| `TARGET_DB_NAME` | БД целевого сервиса (procedures, proposals) |
| `USER_DB_NAME` | БД пользователей и организаций |
| `CLASSIFIER_DB_NAME` | БД классификатора (КТРУ) |
| `LOG_DB_NAME` | ClickHouse-база с логами httpActions |
| `ORG_DB_NAME` | БД организаций |
| `INTERNAL_IP_PREFIX` | Префикс внутренней подсети (исключается из IP-поиска) |
| `GOODS_URI_PATTERN` | URI-паттерн для фильтрации http-логов |
| `KTRU_URI_PATTERN` | URI-паттерн для поиска по КТРУ |
| `PROPOSAL_URI_PATTERN` | URI-паттерн для поиска по предложениям |
| `HOST`, `PORT` | Адрес и порт сервиса |

## Обработка ошибок

| Код | Когда возвращается |
|---|---|
| 400 | Не передан обязательный параметр, неверный формат даты или ИНН |
| 404 | Организация, КТРУ или пользователи не найдены |
| 500 | Внутренняя ошибка при обращении к БД или ClickHouse |

## Примечания

- Использует внутреннюю библиотеку подключения к БД и ClickHouse `supp_adel` —
  в репозитории заменена заглушкой.
- Реальные названия БД, URI-паттерны и внутренняя подсеть вынесены в `config.py`
  и **не коммитятся**.
- Сервис работает с production-БД — креды должны задаваться через переменные
  окружения на уровне `supp_adel`.
